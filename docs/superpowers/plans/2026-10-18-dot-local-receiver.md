# Local dot delivery receiver implementation plan
Approved scope: docs/integrations/dot-scheduled-delivery-proposal-20261018.md, parent request to implement locally while cloud sync setup is pending.

1. Strict shared deliveryVersion1 manifest + READY schemas; keep inbox schemaVersion1 unchanged. Image buffer validation via existing sharp (max20MiB, max25MP, max10000axis, PNG/JPEG/WebP, still image), exact SHA/size/MIME/dimensions. Offline tests.
2. Atomic Core metadata store reusing InboxService: validate every cover corresponds to an exact text item+revision, one required cover per item; commit text candidate+imageasset+cover relation+delivery receipt in one SQLite transaction. Content-addressed bytes are staged before transaction; no accepted receipt until full commit. Same IDs/hashes idempotent, conflicts refused, model_pending state explicit.
3. Fixed fs receiver scans <existingInboxRoot>/deliveries/<deliveryId>/READY.json. Plain filenames only, UTF8 bounded stable regular files, no traversal/symlink/hardlink. Verified input bytes copied into private media/sha256 and staged metadata. Durable retry waiting on missing/sync/IO with 30s/1m/5m/15m; permanent malformed/conflict quarantine status. Atomic receipt rebuild from DB. Scan backlog, not current date only.
4. Wire same existing configured inbox scan/pause path; no cloud API, public server, new credentials, model process, music/publish operation, or formal installed setting change. Show delivery status/path on current inbox UI.
5. Isolated real SQLite tests: old text v1, positive image binding, duplicate/revision/conflict, partial sync, invalid image/hash/path/link/size, crash after commit before receipt/restart, concurrency/retry/backlog and no external effects. Then current-tree typecheck/build, fresh review and local commit.
