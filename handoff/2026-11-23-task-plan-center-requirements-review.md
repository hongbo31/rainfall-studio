# 任务中心与计划中心需求评审稿

日期：2026-11-23（北京时间）  
状态：2026-11-23 完成产品、后端、前端与 QA 的本线程评审；2026-11-24 susu 连续回复“继续”，按推荐默认确认 RF-019 实现口径。本文的历史现状与候选方案保留供追溯，最新决定见[决策单](2026-11-24-rf019-decision-sheet.md)。  
范围：任务中心（发布任务/运行）与计划中心（计划定义/运行/作品项/执行阶段）的状态、异常解释和安全恢复。

## 1. 用户目标

用户应能从一个任务卡快速知道“自动化正在做什么、卡在哪里、是否需要我处理、下一步怎么做”；能进入计划中心看单首和阶段详情；遇到不确定的平台/API 结果时不重复扣费或重复投稿；处理后两个中心能显示同一运行的最新结果。

## 2. 现状（代码与交接证据）

- 任务中心保存发布任务定义。现行 schema 包含手动/定时执行、关联计划、同意状态、版本号等。任务运行状态为 `running`、`waiting`、`action_required`、`completed`、`partial`、`failed`、`stopped`；运行记录有 detail、时间戳、日志和各关联计划进度。
- 计划中心保存计划定义和不可变运行快照，运行下有作品项、阶段尝试、平台发布尝试、定时 occurrence、专辑绑定等记录。Run 状态为 `running`、`waiting`、`blocked`、`stopping`、`stopped`、`completed`、`failed`；阶段包含 `dispatching`、`waiting`、`unknown`、`succeeded`、`failed`、`not_found`。
- 两中心共用计划执行数据。任务中心概览关联计划进度，计划中心呈现运行详情和阶段级动作；同一计划可能存在任务启动的关联运行。已有交接说明同一计划可在两中心各自启动、记录结果及停止，执行归属需在 UI 分辨。
- RF-016：作词进入持久化 unknown 后，约 4 秒刷新只重读状态，并不自动向同步文本 API 对账。缺 usage、请求派发后网络中断、应用重启等可能触发 unknown；来源尚需由每次执行证据确认。盲目重试可能重复生成/扣费。
- RF-017：明确 HTTP 402 或供应商余额/额度错误会产生 `TEXT_PROVIDER_CREDITS_REQUIRED`；两中心已有显著余额提示和配置中心入口。未完成真实供应商错误样本及界面验收。
- 现行实现已含失败阶段重试、部分待处理/待发布、停止后续步骤等路径，但各错误的安全性和用户可理解性并不统一。不能将“前端不断刷新”解释为后台仍在重试。

证据：[RF-016 分析](2026-11-23-ai-lyric-unknown-reconciliation.md)、[RF-017 余额提示](2026-11-23-text-api-balance-warning.md)、`src/shared/publication-tasks.ts`、`src/shared/plan-center.ts`、`src/core/plan-center/index.ts`、`src/renderer/components/PublicationTaskProgress.tsx`、`src/renderer/pages/PlanCenter.tsx`。

## 3. 建议的职责和状态口径（供评审）

- **计划**：可复用的配置与调度定义；编辑/启停影响未来运行。编辑时不得静默改写已开始运行的快照。
- **任务运行**：一次手动/定时任务的总览和关联计划编排。负责说明整体是否运行、等待、需处理、部分完成、失败或已停止。
- **作品项**：该次执行中的单首工作，不用一个计划级结果掩盖其他歌曲的差异。
- **阶段尝试**：一次外部调用/动作的回执状态。`unknown` 表示结果不确定，不能等同仍运行、失败或未发送。
- 任务中心首页提供总进度、异常数、待用户动作数和最近状态；计划中心是配置与执行明细的权威入口。两边使用同一原因和动作，不重复制造不同语义的“完成/失败”。任务启动的关联计划应标注来源/归属；停止或重试范围要让用户在操作前可见。
- 在确认本次执行关联关系前不应合并两个中心的自主启动行为；现存任务、计划、快照和历史记录需保持可读。

## 4. 异常分类与建议动作矩阵

| 类别 | 可判断条件/现状 | 用户提示建议 | 下一步动作建议 | 安全边界 |
| --- | --- | --- | --- | --- |
| 配置/前置条件不足 | 运行前可确定的缺模型、账号、授权、目录或能力 | 指出缺哪项及影响的作品/阶段 | 打开对应配置页；补齐后恢复或新运行 | 尚未派发时才允许恢复原运行；运行快照与计划定义差异需明示 |
| API 余额/额度不足 | 明确 HTTP 402 或供应商余额信号；RF-017 已分类 | 明确“余额/可用额度不足，本次作词已停止” | 配置中心检查 key/计费，充值后由用户重新运行 | 不因余额错误自动循环请求；重跑前校验原执行是否已终止和预算 |
| 明确失败/无副作用 | 有明确拒绝/错误回执且可证明操作未产生副作用 | 失败阶段、具体原因、受影响歌曲 | 有限重试/修复配置 | 只有可证明未提交或平台支持幂等时可重试；避免重放整批 |
| 派发后结果未知 | 请求可能到达，超时/断连/重启/回执缺失；RF-016 发现作词可能长期 unknown | “请求可能已到达，暂不能确认结果；避免再次生成/投稿”并显示等待时长和派发状态 | 若供应商支持，用请求 ID 查询；否则引导人工核对或标记核对结果 | 禁止盲目自动重试；不得把 unknown 自动改为失败/未发送 |
| 用量/账单待核对 | 已有内容或调用回执，但 usage 无法验证；`TEXT_USAGE_UNKNOWN` | 分开说明内容是否可用、账单/预留额度仍待核对 | 显示可验证内容和人工对账入口；只有额度策略允许才继续后续阶段 | 不能将无法确认的用量记为零或释放预留 |
| 上游长时间等待/超时 | 按阶段有超时或等待阈值，需区分服务端处理与本地轮询 | 显示阶段、开始时间、已等待多久、上次确认时间 | 有外部任务 ID 时继续只读轮询；超过阈值提示核对或停后续步骤 | 轮询不能重复收费提交；超时不等价未成功 |
| 用户取消/停止 | stopRequested 表示停止后续流程，部分外部动作可能已发出 | 明确停止范围和仍待确认的外部动作 | 允许停止后续阶段；未完成的外部回执仍可核对 | “停止”不承诺撤销已经发送给平台/API 的请求 |
| 重复点击/重复触发 | 同任务/计划存在活跃运行或 requestId/幂等键冲突 | 显示当前活跃运行和归属，不静默创建第二份 | 打开当前运行；确需另开时用户显式选择 | 保持现有防重复和计划/任务版本检查；不得自动双发 |
| 部分成功 | 单首或单平台结果不同 | 展示成功、失败、待处理的数目及项目 | 只对安全失败项继续；导出/打开详情 | 不因一个项目失败重复已成功项目 |

## 5. MVP 建议与验收场景

MVP 先统一表达与安全动作，不承诺未知结果自动解决：

1. 任务中心卡片展示运行来源、整体状态、完成/待处理/需核对数量、最近更新时间；详情展开可按歌曲查看阶段及行动按钮。
2. 计划中心保留配置与详细运行时间线；从任务中心打开时定位到同一 `runId`，并清楚标注任务来源、计划快照版本和停止范围。
3. 每个异常展示短标题、受影响对象、原因、最后更新时间/等待时长、是否可能已派发、已知外部 request/task ID（脱敏），以及一个明确主动作。
4. 余额/额度不足可直达模型 API 配置；普通网络错误不能显示成欠费；unknown 必须提示“先核对结果，禁止盲目重试”。
5. 同一 plan/run/item/stage 在两个中心状态、reason、运行来源一致；页面刷新/重新打开后历史状态不丢。
6. “重试”前显示精确范围（单阶段、单首或整次运行）及重复扣费/投稿风险；不安全时禁用按钮并说明核对方法。
7. 停止流程中只阻止后续动作，明示已派发操作的最终状态仍可能未知；已完成歌曲不重新执行。
8. 旧任务、旧计划、旧历史、revision/snapshot 能正常读取；新增 UI 不要求迁移生产数据。浏览器和 Windows 客户端共用相同状态及错误语义，关键操作可达性一致。

### 验收案例

- 给定 provider 明确 402，任务卡和计划阶段都呈现余额不足和配置入口，状态不再写成 usage unknown。
- 给定 POST 发送前的确定性配置错误，界面显示未发送/配置错误；给定 POST 后断连，显示 unknown 且不自动再次调用。
- 给定 usage 缺失但歌词正文可读，界面区分“结果/内容”和“用量待核对”，后续是否继续受预算策略控制。
- 给定一个任务关联 8 个计划，其中部分成功、部分等待、一个未知：总览计数准确，单首定位正确，重试不会重复已成功计划。
- 给定一个计划同时在任务中心已有活跃运行，重复触发时看到当前运行和来源；用户停止后，只停止之后的动作并保留已发外部操作的核对状态。
- 断开并重开客户端/刷新浏览器后，run、item、stage attempt 的同一异常仍能定位；不同端显示相同状态名称和恢复限制。
- 用键盘聚焦错误动作和详情入口；界面简洁直说下一步，诊断细节可展开，且错误信息不泄漏 API key 或完整敏感响应正文。

## 6. 评审决策项

以下为产品决策候选，需 xb 收敛，不在本稿当作已决定：

1. Task Center 与 Plan Center 是“总览与明细”的严格职责边界，还是允许各自独立启动同一计划；若保留并行入口，如何显示 owner/source 和冲突。
2. unknown 的人工核对 UI 是只记录核对状态/备注，还是还需供应商查询入口；供应商各异，逐一验证能力后再决定自动对账。
3. usage unknown 但有内容时，是否默认禁止下游继续，还是可由预算/用户策略授权继续；额度保留和内容可用的表达方式。
4. 有明确可重试失败时，人工重试的最小粒度、次数上限、冷却时间和需确认条件。自动重试默认关闭；推荐单项有限人工重试，不重放已成功项。
5. waiting/unknown 超时阈值是否按阶段配置，以及达到阈值后应提醒、阻塞还是只标记需核对。
6. 历史状态的呈现和旧任务迁移：仅前端适配旧状态，还是新增持久化分类字段；推荐先做展示兼容，不迁移/重写历史结果。

## 9. 后端与 QA 快审修订 v2

已将跨角色快审建议纳入验收约束，避免未知结果、已受理回执和余额错误共用模糊状态：

- 请求发送确定性分为**确定未发送**、**发送状态未知**、**确定已受理但最终回执未到**。第一种属于可确认的前置失败/未派发，不得标为 `unknown`；后两种分别提示可能已发送、已受理待终态。平台投稿/专辑操作回执未知单独呈现；明确 HTTP 402 或供应商余额信号才归为余额/额度不足，通用 4xx 不得推断欠费。
- **自动重试禁用**。人工核对需追加 reconciliation observation，记录证据引用、操作者、时间和结论；不得覆盖原始 unknown/attempt。平台 `not_found` 不等于请求未发送或没有副作用。
- 人工重试前须核实副作用已消除或供应商提供可靠幂等保障，并精确限定为单一 `item + stage`；已成功动作不得重跑。停止只阻止后续动作，不承诺撤回已派发请求。
- 明确失败后的重试必须由用户手动触发；服务端核对重试资格、次数和冷却时间。可显示人工冷却提示，不得把冷却渲染为自动重试倒计时。
- 验收分开展示歌词内容、usage 核验和额度 reservation。歌词正文可读不自动代表允许继续评分、改写或音频等耗费型阶段；是否允许继续作为第 6 节待决策项。
- 错误详情尽可能展示 reason、外部 request/task ID、受影响数量和时间。旧记录缺字段时显示“未记录”，数量只按已持久化 item/stage 计数，不推断是否派发或成功；新增持久化字段如必要，采用增量可回退兼容，不改写历史 attempt。
- 两中心服务端需核对 active-run、owner/source 和重复启动冲突。是否允许同计划并行自主运行须先由产品决策；仅禁用客户端按钮不足以形成安全边界。
