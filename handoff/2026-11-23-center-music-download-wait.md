# 两中心原曲下载等待与刷新优化

2026-11-23，北京时间。RF-004 由 backend 排查执行链路，RF-005 由 frontend 排查双端共用界面，qa 负责基线和独立复核，xb 汇总并验证集成构建。

## 排查结果

- 当前浏览器会话的 SQLite 只读记录显示，11:07 至 11:20 有一个谱乐网页下载阶段耗时约 13 分 25 秒后成功归档。核对时没有仍停在 `ORIGINAL_ASSETS_PENDING` 的执行。旧代码领取下载阶段即写该状态，核对原曲、准备 WAV、传输和归档共用一条状态，历史记录无法拆出本次各段耗时。
- 谱乐 API 路径也把原曲未就绪和查询错误写成同一等待。查询按至少 15 秒间隔重复，原实现缺少累计错误和等待上限。旧配置版本或坏回执还可能在领取时拒绝，已有阶段保留原等待，父任务继续占用后续计划的位置。
- 两中心的查询队列把新选择排在旧请求后。旧版隐藏界面在 12 个虚拟秒内首次读取之后又触发 3 次自动读取。Core 查询单条执行的下一阶段或更新阶段状态时，会把无关执行历史一并载入。

## 改动与影响

- `src/main/plan-pule.ts`、`src/main/pule-browser-page.ts`、`src/core/plan-pule.ts`、`src/shared/plan-pule.ts` 在下载阶段区分原曲核对、平台等待、A/B 版 WAV 准备与下载、归档。谱乐网页单版恢复只访问所选原 ID，验证其标题。双版仍分别核对两首。苏诺已暂存 WAV 按原哈希核对后归档。谱乐网页各版沿用每次 10 分钟及有限重试的下载预算。
- API 从本次下载尝试开始计时。满 20 分钟后，下一次正常查询仍缺少要求的原曲时结束本次等待。配置只保留一版时，可下载已就绪的指定原曲，到期可按保留策略使用另一首已验证原曲。连续 5 次查询失败也会结束等待，正常查询重置错误计数。领取阶段识别确定的配置或回执错误并记录结果。父任务可继续后续计划，手动重试下载复用原歌曲 ID。阶段记录使用既有 JSON 字段和可选查询错误计数，旧库可直接读取。
- `src/core/plan-center/index.ts` 按当前执行读取条目、阶段和发布记录。普通原曲保护检查按本次计划范围读取，只有判断旧回执归属时查对应账号的历史。
- `src/renderer/use-center-query.ts`、`src/renderer/plan-execution-labels.ts`、`src/renderer/pages/PlanCenter.tsx`、`src/renderer/components/PublicationTaskProgress.tsx` 共用简短下载状态。旧记录显示「正在获取原曲」。切换选择立即发新查询，晚到的旧结果不能覆盖。前台同一范围串行读取，隐藏时暂停自动轮询，回到前台即时刷新。隐藏期间保留操作后的显式刷新，已开始的有效响应可以显示。
- 回归扩展了 `tests/plan-center.test.mjs`、`tests/plan-workflow-refactor.test.mjs`、`tests/plan-workflow-ui.test.mjs`、`tests/pule-browser.test.mjs`。项目状态记录在 `docs/project/board.md`。
