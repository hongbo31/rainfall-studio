# 曲风感知的动态歌名

## 需求与当前判断（2026-11-27）

- 用户希望所有音乐类型/风格都能生成各自有辨识度的歌名，减少普通和重复；示例包括助眠/催眠/空灵风格以及 DJ 风格，并明确要求拼接规则不能固定。
- 2026-11-27 用户进一步明确采用“核心歌名 + 动态曲风感知”：例如核心名“蹦跳墨尔本”可按歌曲内容生成“蹦跳墨尔本2027年爆款DJ纯音乐”“蹦跳墨尔本爆款DJ纯音乐”“蹦跳墨尔本纯音乐”或“蹦跳墨尔本爆款”。核心名在前，后续描述词数量和组合动态变化；年份/爆款等词不固定、不要求每首出现，年份按创作/发行语境决定，不能硬编码 2027。
- 当前 `src/core/lyric-writing.ts` 的共享提示主要要求短标题、从副歌/场景提炼，缺少对风格线索与近期已用歌名的引导；现有 `title`、`alternateTitle`、语种和标题清理规则需要保留。
- 用户已选择动态曲风引导，避重范围为同批歌曲和同一艺人近期标题。设计暂定最多参考该艺人最近 50 个作品名；保留核心歌名并可动态追加零到多个曲风/形态、氛围/用途、年份/流行感描述，不固定组合；不新增自动付费重试。
- 产品角色只读审查设计后没有提出会改变方案的关键问题。用户已确认设计文档 `docs/superpowers/specs/2026-11-27-genre-aware-song-titles-design.md`，实施计划为 `docs/superpowers/plans/2026-11-27-genre-aware-song-titles.md`，现进入共享 Core 实现和静态审阅。

## 实现范围

- `src/core/lyric-writing.ts` 为新建的人声、纯音乐和灵感生成任务加入统一命名规则。A/B 从本首作品各提炼一个不同的核心歌名，各自按曲风和内容选用零到多个描述词。创作或发行语境明确给出年份时才可加入对应年份。
- 同艺人历史按精确 `artistId` 在 SQLite 内过滤空标题和无效创建时间，按时间倒序，仅返回最多 50 个标题。时间采用项目使用的带时区 ISO 格式，通过实际日历日期校验后才用于排序。计划标题通过 `planAttemptId` 定位当前 `lyric_write` 尝试和条目，SQLite 只返回同一运行中序号更小的条目标题及关联 ID。条目没有可用标题时，按尝试序号倒序核对关联歌词任务，只取选中版本的标题。版本选择沿用定稿 ID、当前 ID、无 ID 旧记录的末版规则。
- 新任务在估价前保存标题字符串快照，领取任务及同一任务的恢复沿用快照。评审、改写和 `creativeBrief()` 重试哈希沿用既有输入。内部艺人 ID 和快照从 `visible()` 剔除，列表也沿用原字段。旧任务缺少快照时沿用原生成提示及预算。
- 这次修改位于浏览器与 Windows 共用的 Core。已有的标题字段、清理和长度校验、预算与预留公式、停止、回执处理和计划并行顺序沿用原流程。

## 验收目标

- 曲风、语种和本首内容会参与标题命名；核心歌名在前，曲风/形态、氛围/用途、年份/流行感描述可按贴合程度动态选用、组合和排序，且可全部省略。
- 提示包含同批与同艺人近期标题作为避重线索，同时维持 A/B 标题差异、现有字符/符号规则。
- 不增加自动模型调用或费用；浏览器和 Windows 使用同一逻辑。
- 用户已授权继续实现；不添加或运行测试，未调用真实付费模型或启动可见客户端。

## 验证与回退

1. 静态核对了三条生成分支、历史标题过滤与排序、计划条目及草稿标题回读、对外字段和旧任务兼容性。第一轮独立审阅发现 SQLite 查询未在取数前限制结果数、日期解析会归一化无效日历日期；提交 `d333591` 后复审确认两项均已修复：SQLite 在返回前过滤和限制 50 条，ISO 校验在时间转换前排除无效日期。`git diff --check` 通过。行为测试、类型检查、构建、模型输出、浏览器端运行和 Windows 原生验收均未执行。当前桌面验证指针未找到，桌面入口未变更。
2. QA 可在之后的授权验收中使用隔离库，为同一艺人、新建的同名艺人及不同计划运行准备有区别的歌名。检查三类生成请求只包含符合范围的历史和同批标题，评审与改写请求无避重字段，并确认旧任务仍可领取。模型表现需另行用实际请求验收，观察核心歌名、A/B 差异、描述词贴合程度及年份省略。标题重复程度以实际输出为准。
3. 回退时从 `src/core/lyric-writing.ts` 撤销本轮提示与上下文收集。回退版本应继续从 `visible()` 剔除已写入任务的内部 `artistId` 和 `titleAvoidance`，避免这些字段随旧版展开返回值；无需迁移作品库。
4. 全分支审阅后的修复改用 SQLite 投影同批标题。已静态核对同一运行、较小条目序号、歌词阶段归属和版本选择规则。条目材料与歌词版本的完整记录无需反序列化到 Core，查询仍只使用已保存的数据。未运行查询行为测试。
5. 复核旧版本数组时补上元素类型保护。读取 ID 或标题前先确认元素是 JSON 对象。无指定版本 ID 时，末版为 `null`、`false`、数字零或空字符串会继续查找更早的尝试。非空字符串等真值末版保留该尝试的优先级，返回空标题。静态核对了随包 SQLite 的 `json_each` 类型和原 JavaScript 回退逻辑，`git diff --check` 通过。未运行行为测试。
6. 用户再次强调目标是 AI 作词生成请求本身的歌名规则。静态复核确认动态指导已附加到人声、纯音乐和灵感生成的 system prompt；发现通用规则“避免给同一个歌名加后缀”可能与允许追加动态描述词冲突，也可能让模型把 2–8 字建议套用到完整标题。已明确该长度建议只适用于核心歌名，两个候选必须有不同核心名，并只禁止通过替换描述词或单纯增删后缀制造候选；完整标题仍遵守 40 字符上限。
7. 保留旧版 `titleGuidance` 原文为 `legacyTitleGuidance`，使不带 `titleAvoidance` 标记的存量生成任务 system prompt 与旧版本逐字一致；仅带标记的新生成任务将该片段替换为优化规则及动态风格指导，人声、纯音乐和灵感分支共用此条件。评分、改写、提炼提示词等阶段不变。该兼容避免旧任务领取时实际 prompt 变长而超过原预算。仅静态核对与 `git diff --check`，未运行测试、类型检查、构建、API 或客户端。
